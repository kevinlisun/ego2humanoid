# Track BT — Blender digital-twin assets + RSI-tuned physics (technical design)

**Status:** adopted as the scene-reconstruction route, **replacing SimFoundry** (owner decision 2026-11-19, after the camera-frame twin render of clip 108 matched the real video; see §6). Original design request 2026-11-17. Tasks: `TASKS.md` → Track BT. Builds on Track RSI
(`docs/notes/track_r_agentic_real2sim.md`); both tracks share `SimParams` and the feedback loop.

## 1. Why

The current scene objects come from monocular reconstruction (SAM 3 crop → image-to-3D → mesh). Batch
review of clips 10/100/101/104/108/114 shows the object bodies are the weakest link:

| Clip | Symptom | Root cause (verified) |
|---|---|---|
| 114 | Held mesh differs from the video duck | The crop is cut from grasp frames (84–165) where the hand occludes it; the mask is two fragments, so image-to-3D produces junk. The clean frame-0 crop (`scene/crop_6.png`, "peg") is not used for the held body. |
| 108 | White stand under the pen is missing | Not a mesh problem: the pen start is computed as table-resting (z 0.788) although it sits on a ~10 cm stand, so the stand is 19 cm from the grip, over `MAX_REGISTRATION_M` (0.15), and the whole inventory is dropped (`unregistered`). |
| 10 | Small object vanishes before placing | It comes to rest at z 0.852, 3 cm above its table-resting height, inside or under a scene mesh (physics and visual disagree). |
| 100, 101 | Object stays stuck to the fingers | Release is taken from the pinch geometry (6.83 s / 7.63 s) but the tactile span ends at 4.27 s / 6.17 s: the object is carried 1.5–2.5 s past the human release. |
| 104 | Object not picked | The fingertips come no closer than 6.8 cm to the object (hand-eye/depth error), so there is no contact at all. |

Blender-quality meshes fix the first class only. The owner decision is to **stop trusting generated
meshes**: build a library of authored, metrically scaled, textured digital-twin assets, bind each clip
object to an asset, and let RSI estimate physics. Reconstruction stays as a fallback and for pose.

## 2. Principles and scope

1. **Perception gives pose, scale hint and identity; assets give shape, colour and physics priors.**
2. **Assets are authored once, reused across clips**: a catalogue keyed by category + colour + size.
3. **Everything is a file and reproducible**: asset id + version + sha256 in the sim bundle.
4. **Fallback never disappears**: no matching asset → today's reconstructed mesh (flagged `asset_source=reconstructed`).
5. **Sharpa only, MuJoCo only**, same as Track RSI.

Out of scope: deformables/articulated assets (v1 rigid only; hinged lids later), automatic asset
generation (the owner authors assets or imports licensed ones), GUI.

## 3. Architecture

```
video ──► perception (SAM 3 inventory, MoGe, VO)  ──►  ObjectObservation(label, colour, size, pose, support)
                                                              │
asset library  assets/twin/<id>/{asset.yaml, visual.glb, collision/*.obj, preview.png}
                                                              │
                          AssetBinder (label+colour+size score, support surface) ──► binding.json
                                                              │
        Blender (bpy, headless): place assets at perceived poses, render ego view ──► twin_render.mp4
                                                              │
              MJCF compiler (visual mesh + CoACD collision + inertia) ──► scene MJCF / BoxObject list
                                                              │
        RSI loop (SimParams: pose offsets, scale, mass, μ, solref, grip, release time) ──► feedback
```

### 3.1 Asset package (`assets/twin/<asset_id>/`)

* `asset.yaml` (schema-validated, versioned): `id`, `version`, `category`, `synonyms`, `colour_hsv`
  (dominant colours), `size_m` (bbox, metres, **authoritative scale**), `up_axis`, `rest_poses`
  (stable faces with probabilities), `grasp_regions` (optional), `physics` (`density_kg_m3` or `mass_kg`,
  `friction`, `restitution`, `source=prior`), `hollow` (container flag + inner floor z), `licence`,
  `author`, `sha256` of every file.
* `visual.glb`: PBR textured, Y-up→Z-up fixed on import, origin at the bottom-centre of the bbox.
* `collision/`: convex pieces from CoACD (`src/stages/reconstruction/scene/collision.py:convex_pieces` already exists),
  ≤ 32 pieces, generated by `scripts/twin_import.py` (the planned separate `build_twin_collision.py` was not written); never authored by hand.
* Conventions are documented in `docs/DATA_CONTRACTS.md` (contract change = dedicated task, HARNESS §2).
* Large binaries stay out of git (HARNESS §5): the library is planned under `data/assets/twin/` (git-ignored; the directory does not exist yet), only `asset.yaml` index + tiny test assets are committed.

### 3.2 Binding (identity → asset)

Score per (observation, asset): `label` match through synonyms (`mug`↔`cup` is already handled in
`stages/reconstruction/objects/place_target._canonical`), colour distance in HSV (hues only trusted, as in `inventory.by_phrase`),
size ratio of the perceived footprint to `size_m` (scale-free within ±35%), and role from the task text.
Output `binding.json` with the top-3 candidates and the chosen one. Below a confidence threshold the
binder reports `unbound` and the clip falls back to the reconstructed mesh. A human can override with a
yaml (`bindings.yaml`), which wins over the binder.

### 3.3 Pose and support (fixes the 108 class of bug)

The asset's `size_m` replaces the perceived size, so the **support surface** is derived from the scene,
not assumed to be the table: the held object's resting z comes from the support asset below it
(`support_id`, top height) when the held xy lies inside its footprint. Registration is performed against
the bound assets' footprints, with the grip-to-support offset reported instead of silently dropping the
inventory.

### 3.4 Blender role

Blender is used **headless via `bpy`** (pip wheel in a dedicated venv, not in the main env) for:

1. **Authoring/import checks**: `scripts/twin_import.py` (logic in `src/stages/reconstruction/objects/twin_import.py`) validates a `.blend`/`.glb` (scale, origin,
   manifold, texture), bakes to `visual.glb`, renders `preview.png`.
2. **Digital-twin render**: place the bound assets at the perceived poses, with the ego camera
   (`intrinsics_est.json`, `camera_poses.npz` for walking clips), render RGB + instance masks; this gives
   the RSI loop a **visual comparator** against the video frame (mask IoU, colour histogram distance,
   LPIPS if available).
3. Optional: HDRI/lighting from the video median colour for a closer match.

Blender never runs inside the physics loop (too slow); MuJoCo renders stay for review videos.

### 3.5 Asset → MuJoCo

Module `src/stages/reconstruction/objects/twin_asset.py`: `load_twin_asset(dir) -> BoxObject` (or a successor that keeps
`mesh_vertices`, textures, collision pieces) that reuses the existing mesh path: `visual.glb` as a
`contype=0` visual mesh, convex pieces as collision geoms, mass from `density × volume`, inertia from the
pieces, friction/solref from `SimParams`. The existing collision proxies stay for the pinch slab until the
hand can grasp the real shape.

### 3.6 RSI integration

Extend `SimParams` (Track RSI.2) with a per-object overlay `objects.<name>.{mass_kg, friction, solref,
solimp, pose_offset_m, yaw_rad, scale}` and the release/hold knobs. Calibration targets, in order:

1. **Timing**: grasp onset, lift, release and settle times against `tactile_timing` and `hold_s`.
2. **Kinematics**: lift height and carry distance against `observed_lift_m` and the demo carry.
3. **Appearance**: twin render vs video (IoU, colour).
4. **Stability**: ≥ 3/5 robustness runs (Track RSI.18).

Search is bounded (≤ 6 parameters per object, ranges from `asset.yaml` priors); coordinate descent per
parameter group, then agent hints from `feedback.json`. This is **estimation of plausible parameters
under monocular evidence**, not a ground-truth identification; results are reported with the parameter
range that keeps QA passing.

## 4. Risks

| Risk | Mitigation |
|---|---|
| Asset authoring does not scale | Start with the 10-clip set (~25 objects), accept `unbound` fallback, track coverage in a table, import licensed packs (check `docs/LICENSES.md`) |
| Scale mismatch vs the real object | `size_m` measured by the owner or from the video's table-plane footprint; binder tolerance ±35%, always report `scale_ratio` |
| Pose error remains (108, 104) | Separate tasks BT.4/BT.5 fix support height and registration; twin assets do not hide perception errors |
| Release timing (100/101) | BT.6 fixes the release source (tactile onset vs pinch geometry); independent of assets |
| `bpy` weight (≈400 MB) and Python pin | Separate venv under `/tmp/venvs`, optional extra, lazy import, no effect on default tests |
| Collision of small/thin assets (pen, 1 cm slab) | CoACD resolution per asset, minimum thickness check in `twin_import.py` |

## 5. Acceptance (system level)

On clips 10, 100, 101, 104, 108, 114 with the twin library: every task object is bound (or explicitly
`unbound`), the MuJoCo and Blender renders show the same objects and colours as the video, no object is
dropped as `unregistered` because of a support-height error, and RSI reports per-clip tuned parameters
with timing error < 0.3 s and QA outcome per clip. Success rates are reported honestly in
`docs/notes/batch_results.md`.

## 6. Decision: Blender twin + RSI replaces SimFoundry (2026-11-19)

**What replaces what.** SimFoundry (stages 1b–12, FLUX clean plate, Copilot VLM relay) is no longer the
scene route. The scene is a Blender digital twin plus RSI-tuned physics. The pipeline is:

1. `scripts/build_twin_scene_cam.py`: MoGe point map × `depth_scale`, table plane and basis, per-object
   oriented footprint and support top, two fitted wall planes, pen start snapped onto its support, colours
   sampled from frame 0. Output `review/twin_scene_cam/{scene_cam.json,hands.npz}`.
2. `scripts/render_twin_cam.py` (bpy, `/tmp/bpy_venv`, Python 3.11): renders in the **video camera frame**
   with per-frame head motion, so frames are comparable to the real video (`review/twin_cam_bt.mp4`).
3. Assets: authored or procedural packages go through `twin_import.py` (`asset.yaml`, `visual.glb`,
   CoACD `collision/`), then `twin_asset.py` maps them to MuJoCo bodies (BT.3/BT.8).
4. Physics: RSI tunes `SimParams` (friction, mass, release) against the human video (BT.7+).

**Why.** SimFoundry needs ~250 GB assets, a VLM relay and a gated FLUX model, and only clip 104 was ever
reconstructed. The twin runs per clip on the devbox and shares meshes between render and simulation.

**Status and limits (honest).** Verified only visually on clip 108 keyframes (0/190/287). Hands are
skeletons, stands and pen are procedural, the black pen and eraser are missing, lighting is not matched,
and head motion uses EgoDex GT poses for this comparison only (a no-GT source is open, see
`estimate_camera_poses.py`). The sim-side 108 `NO_LIFT` is not fixed yet (BT.4: start z and table height
must follow `support.top_m`). The twin is not yet physics-verified.

**Doc consequences.** SimFoundry rows in `docs/TECH_DESIGN.md` §3/§9 and `docs/ARCHITECTURE.md` are
marked legacy; `docs/COPILOT_RELAY.md` and `docs/LICENSES.md` still describe it for clip 104 and are archival.
The SimFoundry code remains in `src/stages/reconstruction/scene/` (`simfoundry_runner.py`, `vlm_relay.py`); `scripts/run_pipeline.sh` only passes `SCENE_DIR` when `data/scenes/egodex_<id>` exists (clip 104).

The MuJoCo ↔ Blender link (state replay, shared `TwinSpec`, feasibility) is in `docs/notes/track_bt_mujoco_blender_link.md`.
